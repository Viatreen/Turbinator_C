# Training architecture and improvement plan

**Architecture reviewed:** Turbinator research implementation, HEAD commit `2f1060175cdfcf4da726d13f238a516abb170992` and its working tree

**Report date:** 2026-10-26

This report assesses the experimental 618M training design and the training code in this repository. The default executable uses a compact C11 SAC model; the architecture and performance claims reviewed below should not be read as measurements of that model. The exact large-network tensor count has been verified, but no completed 618M qualification run or policy-quality result is established here. Code references below identify the reviewed research implementation and its line numbers.

## 1. System map

```text
C++ TUI / mobile server (src/trainer/main.cpp)
    -> launches Python CLI detached worker (python/turbinator/cli.py, ipc.py)
    -> SeasonManager (session.py)
       -> vectorized C++ BatchSimulator through ctypes C ABI (native.py, c_api.cpp)
       -> optional NVRTC CUDA camera renderer (cuda_sensors.py)
       -> actor inference / reference-action mixing / opponent policy
       -> sharded transition replay (fast_sac.py)
       -> FastSAC actor + twin distributional critic updates (model.py, fast_sac.py)
       -> evaluation, PyTorch checkpoints, HDF5 replays, JSON telemetry
```

The reviewed simulator is the environment and reward authority. It advances at a 50 Hz control rate (`dt=0.02 s`) with four physics substeps, so its internal integration rate is 200 Hz (`include/turbinator/sim/constants.hpp:53-54`). `src/sim/batch_sim.cpp` runs many independent simulator instances through a CPU worker pool and exposes batched observations, actions, rewards, termination flags, and truth through `src/sim/c_api.cpp`. `python/turbinator/native.py:255-448` binds that API. The reviewed native trainer executable is mainly a launcher, dashboard, IPC client, and HTTP server; its `train` path invokes `python -m turbinator.cli train --spawn-detached` (`src/trainer/main.cpp:34-138,252-269`). The reviewed learner is PyTorch in `fast_sac.py`.

## 2. Task and sensor contract

The active unified curriculum contains **16 scenarios**: 10 quad-jet scenarios and 6 TALON-6061 BWB scenarios (`python/turbinator/config.py:50-91`). It includes hover, landing, inversion and turbine-failure recovery, slalom/evasion, target interception, close/full arena, BWB cruise, two BWB energy missions, and BWB interception/dogfight/arena. Three older scenarios remain in the registry with zero curriculum weight. The V100 preset uses 256 environments, 36 CPU simulator threads, up to four GPUs, a 256-transition learner batch, a configured 65,536-transition replay capacity, and one update per vectorized rollout step (`config.py:231-257`). The default dataclass values differ from this preset, so each run should identify the selected preset explicitly.

| Item | Shape and source | Meaning |
| --- | --- | --- |
| Observation | 4,148 float values, `config.py:9-19`, `src/sim/sensors.cpp:540-605` | 48 pre-LiDAR scalars (delayed navigation, estimated attitude, IMU, actuators, fuel, cannon), 4,096 ranges from two 16×128 LiDAR heads, then four scan age/validity scalars. |
| Cameras | Four 64×64 `uint8` luma images, `config.py:22-26`, `model.py:733-800` | Forward narrow/wide, nadir, and upward views. Camera stem yields four tokens. |
| Mission context | 10 floats, `config.py:17-18`, `src/sim/batch_sim.cpp:359-365` | Seven scenario intent/tag values and three `tanh`-scaled ENU goal errors. |
| Privileged critic input | 64 floats, `config.py:19`, `src/sim/qualification.cpp:564-620` | Simulator truth such as true pose, goal, wind, opponent, projectiles, and obstacles, supplied to the critic and auxiliary targets during training. |
| Action | 15 values, `constants.hpp:44-45`, `fast_sac.py:60-96` | Four throttle commands, four outer gimbal rates, four inner gimbal angles, cannon azimuth/elevation, and one shoot event. The actor emits normalized values, then the rollout maps them to physical actuator limits. |

There is a consequential distinction between the code's “onboard sensor only” prior description and the actual actor input: the mission vector for arena scenarios includes the **exact opponent position from simulator truth**, transformed to a relative goal error. `Simulator::scenario_target_world_m` returns the opponent position for arena scenarios (`src/sim/qualification.cpp:10-13`), and the batch path inserts that target into the actor's mission values (`src/sim/batch_sim.cpp:359-365`). The opponent actor receives the same kind of truth-derived target (`batch_sim.cpp:377-394`). This should be treated as privileged actor information unless such a target feed is an intended deployable input.

## 3. Network architecture

The main V100 `NetworkConfig` declares `d_model=1536`, 24 attention heads, 12 fusion blocks, FFN width 6144, two 6-expert top-2 MoE modules, an 8-query action chunk, a 2048-hidden-unit world/energy head, and two six-layer distributional critics of width 2688 with 64 atoms on a `[-45,65]` value support (`python/turbinator/config.py:112-143`). A meta-device enumeration of the reviewed model yields **528,338,866 actor parameters and 89,634,176 critic parameters**, totaling **617,973,042 across 298 trainable tensors**. The `src/trainer/mobile_server.cpp:137-139` telemetry values give a different actor/critic split (511,585,994 and 106,387,048) while retaining the same total; those split fields are stale. Xavier/Orin presets instead set `d_model=640`, 10 heads, nine fusion layers, four action queries, and width-1024 four-layer critics (`config.py:260-330`), so these are different tensor shapes rather than identical deployable weights.

The actor (`python/turbinator/model.py:1194-1477`) is composed as follows:

1. `OnboardPhysicsPrior` computes a normalized reference action from the 4,148 observation values and mission vector (`model.py:58-113`). A running normalizer processes 52 proprioceptive and scan-quality values. Twenty-four derived tactical features plus the 15-value prior are fed to the proprio and mission stems (`model.py:1034-1192,1205-1231`).
2. A circular-convolution LiDAR stem yields four directional tokens from dual scans (`model.py:800-855`); a shared convolution and spatial soft-argmax camera stem yields four camera tokens (`model.py:733-800`). Two scalar stems and these eight sensor tokens give ten tokens per control step (`model.py:1233-1240`).
3. Twelve pre-normalized attention/FFN fusion blocks process those tokens. MoE blocks are inserted after the middle and last fusion layers; a reflex skip path combines proprio, mission, tactical features, and prior. The summary is a concatenation of the reflex vector and token average (`model.py:1242-1297,1308-1390`).
4. Eight learned action queries cross-attend to sensor tokens. The action head predicts a small gated residual around the physics prior, then uses a squashed Gaussian for the immediate 15-value action. The code supervises all eight action means but only executes the first (`model.py:900-949,1393-1477`). The 15th action is thresholded into a shoot event by the action transform (`fast_sac.py:60-80`).
5. A training-only nine-output auxiliary perception head predicts target/goal, wind/clearance, and hazard quantities. The optional world/energy head predicts a next latent plus 16 physical values. The critic receives the actor's 3,072-wide sensor summary, the privileged 64-vector, and the normalized 15-action; its two separate networks each produce 64 categorical logits and expected Q values (`model.py:1005-1027,1263-1297,1479-1596`).

This is an **asymmetric actor-critic**: the actor does not receive the 64-vector directly, while the critic and auxiliary supervision do. The mission-position caveat above still applies.

## 4. Rollout and learner

`SeasonManager.run_training` creates or resumes a season, builds the learner and native batch simulator, optionally accelerates camera rendering, and samples new scenarios when environments finish (`python/turbinator/session.py:434-681`). Scenario slots alternate BWB and quad-jet, giving a 50/50 split by rollout slot in the unified curriculum; within each vehicle, scenario weights are normalized (`session.py:539-605`). Non-arena scenarios are marked mastered after at least 20 episodes and their recent qualification fraction crosses the scenario gate, but retain 15% of their original sampling weight in the implementation (`session.py:543-563,889-910`). The source comments and README that say mastered tasks receive zero rollout weight do not describe this current code path.

Each 256-environment rollout step:

1. Takes C++ observations, mission, camera, and privileged critic features. If CUDA camera rendering is available, it exports scene arrays from C++, copies them to GPU, ray-traces camera pixels, then copies the result back to CPU (`session.py:630-653`, `cuda_sensors.py:261-300`). The LiDAR used by the learner is still produced in the simulator observation path. An NVRTC LiDAR kernel template exists, but this training loop instantiates only `NvrtcGpuCameraAccelerator` (`session.py:513-528`).
2. During initial warmup, executes noisy reference-controller actions. After warmup, samples the actor and blends its normalized action with a per-episode reference action using `beta`; the reference selection probability decays from 0.45 toward 0.05 over four million environment steps (`config.py:173-192`, `session.py:607-620,824-845`).
3. Steps the batch simulator, records rewards and terminal/truncation flags, updates scenario statistics, resets finished environments, and writes observation/action/next-observation tuples to replay (`session.py:869-985`). A truncation gets a pre-reset next state and a zero terminal mask so Bellman bootstrapping remains possible. A true termination gets a terminal mask of one (`session.py:920-984`).
4. Samples uniformly from replay after warmup, performs the preset's number of updates, and advances cosine actor/critic learning-rate schedulers (`session.py:989-1000`).

Replay stores current and next 4,148-value observations and 10-value missions as FP16, four cameras as `uint8`, and privileged states/actions/rewards/dones as FP32 (`fast_sac.py:98-217`). It has one ring-buffer shard per GPU, initially mirrors batches until each shard reaches 1,024 entries, and subsequently writes round-robin (`fast_sac.py:218-285`). The V100 preset configures 65,536 total transitions; four shards would each be configured for 16,384 entries before memory-based capacity checks. There is no replay persistence in `FastSACAgent.state_dict` (`fast_sac.py:1398-1411`).

The learner forms a clipped double-Q, entropy-adjusted Bellman target and projects it to the 64-atom HL-Gauss categorical support. It minimizes two critic cross-entropies. Actor training combines a gated, scaled SAC policy term; residual-size regularization; nine-value auxiliary perception loss; and advantage-gated reference action-chunk imitation (`fast_sac.py:310-434,1208-1364`). For the large multi-GPU path, a one-step world/energy latent loss and an MoE balancing term are also included (`fast_sac.py:372-406`). The policy Q term uses the deterministic first action-query mean while its entropy term uses the sampled action log probability, so this is a modified SAC objective (`fast_sac.py:352-370`). Q-driven actor learning is disabled until 1,000 learner steps and scaled by 0.05; reference guidance is weighted 0.85 down to 0.35 in the session (`fast_sac.py:363-382`, `session.py:991-999`).

The V100 path keeps persistent actor/critic replicas and replay shards per GPU. Each replica performs local optimizer updates; model parameters are averaged and broadcast every 32 learner steps, while the optimizer states are not averaged (`fast_sac.py:767-895,1011-1125`). The large-network branch uses eager work on CUDA streams; the smaller-network branch may replay captured CUDA graphs (`fast_sac.py:1011-1075`). The large CUDA branch uses RMSprop to reduce optimizer memory, while CPU/smaller branches use AdamW (`fast_sac.py:521-565`). Automatic mixed precision is configured for CUDA (`fast_sac.py:479-481,565-575`).

## 5. Evaluation, artifacts, and operational control

The default deterministic evaluator runs four trials per curriculum scenario using fixed held-out seed ranges and up to 1,505 control steps per trial. It reports success/qualification fraction, reward, episode length, gates passed, and category means (`python/turbinator/session.py:66-181`). Arena success codes include wins, while civil missions use the simulator's success outcome. Periodic evaluation and checkpointing default to every 15 minutes (`session.py:434-448,1089-1169`). A “best” checkpoint is selected from a score combining qualification rate and mean reward (`session.py:1136-1152`).

Season artifacts include `season_manifest.json`, `live_status.json`, `metrics_history.jsonl`, `eval_history.json`, initial/latest/best and step PyTorch checkpoints, HDF5 trajectory replays, replay JSON metadata, and IPC status/command/ack/log files (`session.py:337-425,1154-1273`, `record.py:22-40`, `ipc.py:81-160`). The PyTorch agent state stores actor, EMA actor, critic, target critic, entropy parameter, gradient-step count, model metadata, and config; it does **not** store optimizer/scheduler state, replay, sampler RNG, environment state, or current curriculum episode state (`fast_sac.py:1398-1411`, `session.py:478-504`). Thus resume restores weights and counters but not an exact training trajectory. The C++ TUI and phone server read these artifacts and send control commands over file-based IPC (`src/trainer/main.cpp:113-138,252-299`, `ipc.py:81-160`).

The reviewed CMake target builds C++ simulator tests of determinism/serialization, turbine spool response, reference scenarios, physics, and sensors (`CMakeLists.txt:57-65`, `tests/test_sim.cpp:22-418`). The reviewed CMake file does not register learner-level numerical tests, multi-GPU equivalence tests, or held-out policy regression tests. Simulation tests are valuable but insufficient as acceptance criteria for a complete training system.

## 6. Recommended improvements, ordered by impact

| Priority | Evidence and consequence | Concrete change and acceptance check |
| --- | --- | --- |
| **P0: Remove arena truth leakage from actor inputs** | The mission target is the exact opponent position, read from truth and passed to both players (`src/sim/qualification.cpp:10-13`, `src/sim/batch_sim.cpp:359-394`). This lets the policy track an opponent without detecting it through cameras/LiDAR and can inflate evaluation. | Define a deployment-valid mission contract. For arena, provide only a commanded region or a sensor-derived opponent estimate. Keep exact opponent pose exclusively in the 64-value critic input. Re-evaluate a trained policy with truth-derived mission coordinates disabled. |
| **P0: Make self-play actually act on every intended step** | The session computes learned opponent actions only when the vectorized step index is divisible by four (`session.py:850-867`), but `BatchSimulator::step` clears its opponent-action flag after every step (`src/sim/batch_sim.cpp:410-429`). Consequently the learned opponent is used on one step in four and the reference opponent handles the others. | Query the opponent actor on every step (or make a deliberate four-step action hold in the simulator). Instrument the percentage of arena steps controlled by learned opponents and require it to equal the configured schedule. |
| **P0: Correct the hybrid shoot-action probability** | The sampled 15th action's noise is scaled by 0.15, but the Gaussian log-probability calculation still divides by the unscaled standard deviation (`model.py:1430-1455`). The executed event is binary after a threshold (`fast_sac.py:60-80`), while entropy tuning treats all 15 dimensions as continuous (`fast_sac.py:507-510`). | Model shoot with a Bernoulli head and log probability, or derive the exact transformed density for the current sampling rule. Check sampled action frequencies against computed log likelihood, and test entropy tuning separately for continuous and discrete parts. |
| **P1: Use valid next states for auxiliary world-model targets** | The normal rollout path resets terminated environments before collecting `next_obs` (`session.py:956-984`); the multi-GPU world head then predicts that `next_summary` without a terminal mask (`fast_sac.py:374-390`). Terminal transitions therefore teach cross-episode dynamics. | Capture pre-reset next observations for all done environments, or mask world-model losses for terminal/truncated transitions. Test terminal transitions with a deliberately different reset state. |
| **P0: Use per-vehicle physical action mapping in evaluation and recording** | `FastSACAgent.select_action` maps output cannon azimuth using `vehicle_mode == "bwb"` (`fast_sac.py:594-751`). The unified mode therefore maps every BWB policy action with the quad-jet cannon center. Training later discards this physical output and remaps the normalized action per environment (`session.py:834-845`), but deterministic evaluation uses the already mapped physical output directly (`session.py:106-119`). | Pass a per-environment BWB mask to action selection or centralize action mapping at the simulator boundary. Compare physical action 12 for a mixed BWB/quad batch and verify deterministic BWB evaluations use the BWB center. |
| **P1: Make CPU and CUDA objectives identical** | World/energy and MoE auxiliary losses exist in `_FastSACParallelLossModule` (`fast_sac.py:372-406`), while `_update_eager` ends its auxiliary term after the nine-value target (`fast_sac.py:1299-1339`). Algorithm behavior changes with backend. | Implement one backend-neutral loss specification and compare per-term losses/gradients for a fixed small batch on CPU and CUDA within tolerance. |
| **P1: Fix evaluation granularity and policy selection** | Four trials per scenario produce success rates only at 0/25/50/75/100%, making gates such as 0.78 or 0.90 effectively require 100% in a single evaluation (`config.py:50-91`, `session.py:66-181`). The “best” checkpoint can be selected from noisy small samples (`session.py:1136-1152`). | Use more fixed held-out seeds, confidence intervals, and a separate untouched test set. Select checkpoints on stable aggregate metrics, and report per-vehicle scores so a gain on one aircraft does not hide regression on the other. |
| **P1: Save fully resumable state** | Checkpoints omit optimizers, cosine schedulers, replay, RNG, and simulator/curriculum state (`fast_sac.py:1398-1411`, `session.py:478-504`). | Version a portable checkpoint that includes all training state, with explicit schema and checksums. Compare uninterrupted and interrupted/resumed runs over a deterministic short horizon. |
| **P1: Improve multi-GPU optimization consistency** | Independent RMSprop/AdamW optimizers evolve between 32-step parameter averages; their optimizer moments are not synchronized (`fast_sac.py:767-895,1011-1125`). | All-reduce gradients before each update or synchronize optimizer states along with parameters. Compare one- and multi-GPU updates on a fixed batch. |
| **P1: Derive model counts from the tensor inventory** | The reviewed actor and critics have 528,338,866 and 89,634,176 parameters, but `src/trainer/mobile_server.cpp:137-139` reports 511,585,994 and 106,387,048. The total agrees while the split does not. | Generate telemetry counts from model tensors at startup or a checked build artifact; assert actor, critic, and total counts in a model-layout test. |
| **P2: Avoid computing all MoE experts** | `TalonAeroEnergyMoE.forward` evaluates all six experts, stacks all outputs, and gathers only top two (`model.py:983-1002`). The routing is sparse in output but dense in compute/memory. | Group tokens by selected expert and execute only selected experts, or use an explicitly dense layer if sparse dispatch is slower at ten tokens. Benchmark forward/backward time and VRAM at the actual batch size. |
| **P2: Add opponent diversity and replay coverage checks** | Rollouts use the current policy as opponent after a threshold and the reviewed training path has no historical opponent pool (`session.py:829-867`). Initial replay mirroring and subsequent round-robin sharding can also change scenario mix per shard (`fast_sac.py:245-280`). | Add lagged checkpoint opponents and report head-to-head results against several generations and the reference controller. Track sampled scenario/vehicle frequencies per replay shard and stratify if they drift. |
| **P2: Repair replay-mode classification** | `record_episode` recognizes BWB scenarios only 22–24 and arena scenarios only a limited set (`record.py:39-48`), excluding BWB energy dogfight (27) while the session requests a `self_play` replay for it (`session.py:1120-1133`). | Use the central scenario registry's `is_arena`/vehicle metadata in replay recording. Assert each saved replay's scenario ID, vehicle, and opponent policy mode match the request. |

## 7. Suggested validation gates

1. **Simulation contract:** run fixed-seed, 50-step checks for every active scenario, including raw 4,148-value observations, mission vectors, privileged features, camera/LiDAR buffers, 15-value physical actions, rewards, outcome codes, and termination/truncation flags. Include zero wind in arena and the full BWB electrical power budget.
2. **Learner math:** check fixed tiny tensors for action scaling, sampling/log probabilities, distributional projection, critic/actor/auxiliary losses, one optimizer step, EMA targets, and CPU versus CUDA outputs. These tests should expose the hybrid-action and backend-loss issues before long training.
3. **Runtime validation:** build CPU-only C11 and optional CUDA C configurations with CMake; run tests without Python or C++ runtime dependencies. Verify checkpoint save/load, exact resume, IPC commands, telemetry, and replay metadata.
4. **Training outcome:** run short deterministic smoke training and longer held-out qualification for each vehicle separately, then joint 50/50 training. Record throughput, VRAM, return, success, self-play opponent coverage, and seed variance. A successful build alone does not establish the 618M policy's behavior.

These gates distinguish simulation fidelity, learner correctness, and achieved policy quality.

## 8. Current C/CUDA C implementation and resource plan

The C11 network inventory lists **617,973,042 trainable parameters in 298 tensors**: 528,338,866 actor parameters and 89,634,176 across the twin critics. Its layout test passes and the counts agree with a meta-device enumeration of the reviewed model. The reviewed `src/trainer/mobile_server.cpp:137-139` hardcodes the same total with an incorrect actor/critic split, so status displays should derive their counts from the checked tensor inventory.

The default C trainer uses a compact CPU SAC model. The full CUDA C build defines GPU operations, replay, RMSprop, SAC losses, and the large actor/critic interfaces, alongside CUDA sensor kernels. CMake targets CUDA architecture `70` by default and links the CUDA runtime and cuBLAS; the full GPU trainer requires compute capability 7.0 or newer. Its current defaults are a two-transition minibatch and 512 replay transitions per GPU, with up to four GPU devices selectable. The CUDA build passes CTest, including numerical checks for linear backward, LayerNorm backward, optimizer behavior, and four golden tactical/prior fixtures. A one-V100 learner smoke completed two simulator steps and two optimizer updates with finite actor and critic losses. Checkpoint save/load restored an update count and advanced it, while four V100s completed 32 updates through the replica synchronization interval. An opt-in full-network smoke found finite outputs and nonzero gradients in the LiDAR and camera stems, early and late fusion, MoE routing, action head, auxiliary and world heads, and both critics. Longer training and held-out flight quality still require validation.

The FP32 parameter inventory occupies 2,471,892,168 bytes (2.30 GiB). The GPU trainer allocates current parameters, parameter gradients, target parameters, and one RMSprop square-average value per parameter, so those arrays alone require **9,887,568,672 bytes (9.21 GiB) per GPU**. Replay currently stores two FP32 observations, two `uint8` four-camera sets, mission and privileged vectors, actions, reference actions, rewards, and done flags: **66,672 bytes per transition**. That is about 32.6 MiB for the default 512-transition device shard or 1.02 GiB for a 16,384-transition shard. Activations, minibatch scratch, CUDA context, and cuBLAS workspace increase the peak. A 16 GiB V100 is a practical starting point; batch size, replay size, and measured peak memory must determine the actual supported configuration.

The Android Gradle project packages the C NativeActivity and CMake native libraries for arm64 and x86-64. A debug APK built with JDK 17, Android SDK Platform/Build Tools 35, NDK 27.2.12479018, and CMake 3.22.1 was installed and launched on an Android 35 emulator. Its signature and 16 KiB ZIP/ELF alignment were checked. The Android app shows local simulation and polls trainer status; it does not execute the GPU learner on the phone.

### P3000 laptop configuration

The `p3000` CMake preset selects Pascal `sm_61`, a Release build, AVX2 CPU code where supported, and the compact C11 SAC learner with batched CUDA sensor feature extraction. The 618M learner is excluded from this configuration because its current FP32 parameters, gradients, targets, and optimizer moments alone occupy 9.21 GiB. The laptop path keeps compact model, replay, and optimizer state in host memory; at its default 32-environment batch, its persistent CUDA feature arrays occupy about 1 MiB plus CUDA context memory. A fixed-input parity test compares all 142 CUDA features with the C11 extractor. The preset's five tests and a short training run (320 environment steps, nine optimizer updates) passed on an available 2 GB Pascal GPU. The Quadro P3000 itself was not available for timing.

### Current learner follow-ups

The 618M CUDA actor currently chooses deterministic mean actions during rollout; its SAC loss uses an analytic entropy proxy rather than a reparameterized stochastic policy. It uses one-moment RMSprop, and loading a checkpoint starts with empty replay. The online Welford proprio normalization update is also absent. The highest-value next checks are a small-batch stochastic action/log-probability gradient test, a checkpoint resume test that includes replay and RNG state, and measured qualification on held-out quad-jet and BWB scenarios. In a ten-step comparison on the available P620, the Release/AVX2 hybrid path took 3.37 s while the same executable's C11-only feature path took 2.74 s; CUDA preprocessing did not improve that short run's throughput. Benchmark the P3000 preset on its intended laptop and choose the best batch size and feature backend from those measurements.
